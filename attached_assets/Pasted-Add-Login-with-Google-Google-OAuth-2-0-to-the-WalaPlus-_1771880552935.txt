Add "Login with Google" (Google OAuth 2.0) to the WalaPlus QMS Dashboard so users can sign in with their Gmail/Google account. Keep the existing flow (e.g. admin key for /admin and /qms) as an optional alternative where it exists.

## Requirements

### 1. Login page / entry point
- Add a dedicated login page (e.g. route `/login` or `login.html`) that the user sees when not authenticated.
- On this page, show a clear **"Sign in with Google"** (or "Login with Google") button as the primary option.
- Optionally show a divider and "Or continue with Admin Key" (or link to admin key entry) for existing admin flows, so current behavior is preserved for admins.

### 2. Google OAuth flow
- **Backend:** Implement Google OAuth 2.0:
  - Environment variables: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and a redirect URI (e.g. `https://qms-dashboard.replit.app/api/auth/google/callback` for production and `http://localhost:5000/api/auth/google/callback` for local).
  - Route 1: `GET /api/auth/google` — redirects the user to Google's consent screen (build the authorization URL with client_id, redirect_uri, scope openid email profile, response_type=code).
  - Route 2: `GET /api/auth/google/callback` — receives `code` and `state` from Google; exchange code for tokens; get user info (email, name, picture) from Google; create or update the user in our database (if we have a users table); create a signed session (cookie or JWT) using the existing `SESSION_SECRET`; redirect the user to `/` or the dashboard.
- **Frontend:** The "Sign in with Google" button should navigate to `GET /api/auth/google` (full page redirect or link), so the user goes to Google, signs in, and is sent back to our callback then to the app.

### 3. Session and auth checks
- After successful Google login, set a signed session cookie (or return a JWT that the frontend stores and sends). Use `SESSION_SECRET` for signing. Session should include at least: user id or email, name, and a way to identify the user for RBAC if we have roles.
- Add a backend route e.g. `GET /api/auth/me` that returns the current user from the session (or 401 if not logged in). The frontend can call this to show "Logged in as …" or to gate pages.
- Optionally: for routes that currently require admin (e.g. /admin, /qms), allow access if either (a) valid X-Admin-Key / admin key is provided, or (b) the user is logged in via Google and has an admin role (if we have roles in the DB). If we don’t have roles yet, keep admin key as the only way to access /admin and /qms for now.

### 4. Logout
- Add `POST /api/auth/logout` (or GET) that clears the session cookie (or invalidates the token) and redirects to `/login`.

### 5. Protecting the app
- If the user is not logged in and has no session, redirect them to `/login` when they try to open the main dashboard (/) or other protected pages. Public pages (e.g. login, guide) should remain accessible without login.
- Ensure the login page is the default landing when not authenticated, and after login redirect to `/` or the page they tried to open.

### 6. Tech stack (already in use)
- Backend: Mastra + Hono (Node.js, TypeScript), routes in `src/mastra/index.ts` or a dedicated auth route file.
- Frontend: Static HTML in `dashboard/` (e.g. `dashboard/login.html`), Tailwind.
- Database: PostgreSQL; add or use a `users` table to store Google user id, email, name, picture, last_login if needed.
- Secrets: Use `SESSION_SECRET` for session signing; add `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in Replit Secrets / env.

### 7. Google Cloud setup (for the implementer)
- In Google Cloud Console: create OAuth 2.0 Client ID (Web application), add authorized redirect URIs: production URL (e.g. https://qms-dashboard.replit.app/api/auth/google/callback) and local (e.g. http://localhost:5000/api/auth/google/callback). Use the client ID and client secret in env.
